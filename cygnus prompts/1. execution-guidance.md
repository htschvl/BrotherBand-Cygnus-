> **Context**: Existing DDD/Hexagonal structure (`internal/{adapter,domain,usecase,infrastructure}`), custom Chi middlewares, a `platform/logging` package, `api/openapi.yaml`, and `scripts/split-openapi.py`.  
> **Goal**: Replace manual OpenAPI with Huma (code‑first OpenAPI 3.1), replace logging with zerolog (human‑friendly terminal output), serve Scalar UI for monolithic + per‑resource specs, replace the Python split script with a Go filter inside Huma, and add production‑ready enhancements (graceful shutdown, hot reload, rate‑limit metrics, benchmark tests).

## Principles to follow (read before starting)

- **Preserve existing business logic** – only change the delivery layer (handlers) and logging.
- **No unnecessary code snippets** – infer from existing codebase.
- **Use `testify` for all new tests** – follow existing patterns and integrate with huma tests when possible.
- **Make the Scalar UI beautiful** – use a modern theme, enable dark mode, add examples. **Must use CDN only** – do not vendor.
- **Logging must be extremely detailed** – every request, every DB call (if possible), every error.
- **Best practices** - Clean Code, and other best practices.

### Best Practices, SOLID, Clean Code & Self‑Documentation

- **Single Responsibility** – Each Huma handler should only map HTTP concerns. No business logic, no direct DB access.
- **Open/Closed** – Adding a new endpoint means registering a new Huma operation; existing handlers remain untouched.
- **Liskov Substitution** – Use interfaces for dependencies so you can swap implementations without breaking handlers.
- **Interface Segregation** – Keep use case interfaces small.
- **Dependency Inversion** – Handlers should depend on abstractions, not concrete repositories or external packages.
- **Clean Architecture** – Respect the existing layers. Never let a handler import `infrastructure/postgres` directly.
- **Self‑documenting code** – Use descriptive variable names, no magic numbers. Huma’s `doc` struct tags should contain clear descriptions.
- **Error handling** – Always return `huma.Error` with appropriate HTTP status and a human‑readable message. Never expose internal error details.
- **Comments** – Only when the “why” is not obvious. Prefer expressive code.
- **Consistency** – Follow existing naming conventions, file layout, and test patterns.

**Actively enforce these principles during implementation. If you see a violation, refactor before writing new code.**
